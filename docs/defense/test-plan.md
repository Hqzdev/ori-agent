# План функционального тестирования Ori

Проверяем текущие приложения Ori для macOS и iPhone, их общие данные и сервисы, которые вызываются из приложения. В матрицу входят рабочие сценарии из текущего кода. Маркетинговый сайт, отдельные веб-клиент и CLI, Android, Windows и сценарии только из ТЗ или демонстрационного режима находятся вне объёма. Встроенный браузер и встроенный терминал Mac входят в объём.

## Подготовка

- Зафиксировать SHA сборки, версию ОС, устройство, конфигурацию и дату прогона. Запустить по одному экземпляру Ori на физическом Mac и iPhone. При запуске из Xcode отключить точки останова на время прогона. Сборки запускать с проверенными назначениями My Mac и подключённый iPhone. Перед большой сборкой проверить наличие 20 GiB и переиспользовать проектные каталоги сборки.
- Подготовить два тестовых аккаунта Ori, тестовые Google и Яндекс ID, папку с небольшим Git-репозиторием, скан и известный набор файлов, локальную страницу с полем и кнопкой, тестовые подключения и одноразовый аккаунт для сценария удаления. Проверки записи использовать только с тестовыми получателями, папками и календарями. Платёж проверять в настроенной тестовой среде.
- Для браузера использовать локальную страницу, где можно проверить фактический DOM и счётчик нажатий. Для модели оставить один прогон с реальным провайдером. Повторы, отказы и обрывы воспроизводить детерминированными тестами там, где они есть.
- Отмечать отдельно **пройден**, **ошибка**, **заблокирован** и **не проверен** по каждой платформе и интеграции. Отсутствие ключа, тестового аккаунта или физического устройства означает «заблокирован» с причиной. Результат теста пакета и результат в реальном интерфейсе фиксировать отдельно.

## Быстрый прогон перед защитой

1. На Mac войти через Google, дождаться открытия рабочего пространства, перезапустить Ori и проверить восстановление сессии. При отказе сохранить этап из журнала AccountSession. Ориентир по времени 5 минут.
2. Открыть старый чат **Neon** с браузерными карточками, переключиться на другой чат и вернуться. Создать тестовый чат и получить живой ответ. Проверить историю после перезапуска. Ориентир 5–8 минут.
3. Открыть локальную тестовую страницу во встроенном браузере. Попросить агента прочитать выбранную вкладку, затем вызвать действие с карточкой согласования. Отклонить первый запрос, повторить его и одобрить один раз. Сверить поле или счётчик на странице. Ориентир 8–10 минут.
4. Прикрепить тестовый файл с заранее известным числом, попросить агента извлечь его и создать страницу Library. Открыть фактически сохранённую страницу. Если агент сообщил об успехе, а страницы нет, зафиксировать ошибку. Ориентир 5 минут.
5. На физическом iPhone, если он подключён, войти тем же тестовым аккаунтом, открыть историю и проверить появление одного нового текстового сообщения между устройствами. Ориентир 5–10 минут.

Сначала проверить этот набор. Полный прогон выполнить по матрице ниже.

## Автоматические проверки и отчёт

- Запустить существующие тесты SwiftPM для OriWorkspace, OriAppleIntegrations и OriWidgetSupport. Для общей совместимости использовать OriDomain и OriAPI с реальными HTTP fixtures, Java Gradle checks и `python3 scripts/check-v3-schemas.py`. Для сервиса авторизации использовать `npm run test:auth` из `landing`. Это проверка API для Apple-клиентов.
- Для целевых регрессий переиспользовать скрипты из `scripts/`: `check-browser-execution.sh`, `check-conversation-card-ui.sh`, `check-native-xpc.sh`, `check-session-files.sh`, `check-voice-chat.sh`, `check-chat-performance.sh`. Сценарии физического iPhone использовать только после подтверждения назначения. Прогон с подставной моделью или тестовой страницей указывать явно.
- Запись результата: **ID | SHA | устройство / ОС | тестовое окружение | фактически | статус | снимок или очищенный лог | ссылка на дефект**. Для дефекта записать минимальные шаги и воспроизводимость. Для внешних действий приложить подтверждение из тестового сервиса вместо одного лишь ответа агента.
- Для показа нужен пройденный быстрый прогон на выбранном устройстве. Для отчёта о полной работоспособности у каждой строки должен быть результат. Любой блокирующий дефект во входе, чате, сохранении данных или подтверждениях отмечается отдельно. Непроверенные функции указываются явно.
